# Контекст проекта: параллельный анализатор серверных логов

## Назначение
Групповой учебный проект по параллельному программированию на Kotlin/JVM. Команда — 4–5 студентов, срок около 4 недель, максимум 15 баллов. Программа анализирует большие HTTP access logs, сравнивая последовательную и несколько параллельных реализаций.

## Требования задания (group_project.pdf)
- Описать задачу, вход/выход, алгоритм и причины пригодности к параллелизации; согласовать тему с преподавателем.
- Реализовать последовательную и параллельную версии и проверку корректности.
- Объяснить распределение работы и синхронизацию/обмен данными.
- Экспериментально исследовать размер задачи, число потоков/процессов, время; рассчитать ускорение и эффективность, представить таблицы и графики.
- Проанализировать неидеальное ускорение, узкие места и момент насыщения.
- Общий удаленный репозиторий, src/, Makefile, README.md, report.pdf (4–6 стр.), presentation.pdf; защита 10–15 мин.
- В исходном PDF формула Speedup, вероятно, перевернута. Стандартная формула: S=T_seq/T_parallel; E=S/P. Уточнить у преподавателя при необходимости.

## Входной формат
Одна строка:
`2026-11-01 00:00:00 192.168.1.10 GET /api/users 200 45`
Поля: дата, время, IP, HTTP-метод, URL, HTTP-статус, длительность запроса в мс. Есть синтетический файл `access_large.log` (~87.6 MB, 1.5 млн строк); он не включен в этот контекстный документ — положить его отдельно в data/ или указать путь.

## Выход
Общее число запросов, распределение статусов, топ URL и IP, среднее время ответа, статистика по минутным окнам (пики запросов, ошибки 5xx, средняя/максимальная задержка), время выполнения. Желателен экспорт результатов и бенчмарков в CSV/JSON.

## Предложенная архитектура (не считать реализованной)
- `LogEntry`: дата/время, IP, метод, URL, статус, responseTime.
- `LogParser`: преобразование строки в запись, политика для ошибочных строк.
- `LogStatistics`: локальные счетчики и `merge`.
- `LogAnalyzer`: интерфейс `analyze(Path): LogStatistics`.
- `SequentialAnalyzer`: BufferedReader, построчный парсинг и агрегация.
- `ParallelAnalyzer`: один Reader формирует батчи, `ExecutorService` обрабатывает их; каждая задача возвращает локальную статистику, главный поток объединяет результаты. Ограничить число незавершенных задач (backpressure), иначе очередь `newFixedThreadPool` неограниченна.
- `PipelineAnalyzer`: альтернативная архитектура Readers -> bounded BlockingQueue -> Parsers -> bounded BlockingQueue -> Aggregators -> merge. Корректно завершать конвейер, обрабатывать исключения и не терять записи.
- Дополнительно сравнить общую `ConcurrentHashMap` и локальные `HashMap`, статическую и динамическую балансировку; опционально FileChannel с выравниванием границ строк.
- BenchmarkRunner: прогрев JVM, несколько повторов, медиана, CSV, графики.

## Обработка батчей
Reader читает строки последовательно через `Files.newBufferedReader`, набирает, например, 10 000 строк, передает отдельный список в пул потоков, сразу читает следующий батч. Воркеры обрабатывают одновременно. Когда лимит in-flight батчей достигнут, Reader ожидает освобождения слота. После EOF отправить неполный батч, дождаться всех задач, слить статистику. Не модифицировать список после передачи воркеру.

## Эксперименты
- Число потоков: 1, 2, 4, 8, 16.
- Объем данных: от 100 тыс. до 10–100 млн записей, по ресурсам.
- Размер батча: 1 тыс., 10 тыс., 100 тыс.
- Сравнение sequential, batch parallel, pipeline; локальная против общей агрегации.
- Измерять полное время анализа, учитывать I/O, CPU, память/GC, очереди, синхронизацию. Сравнивать результаты на одинаковых входах; точность через JUnit.

## План разработки

2. Последовательный анализатор.
3. Batch + ExecutorService + bounded in-flight.
4. Проверка полного равенства результатов.

## Важные договоренности
- Язык Kotlin/JVM, Gradle Kotlin DSL, JUnit 5.
- Пользователь хочет писать программу самостоятельно. Codex должен объяснять архитектуру, помогать с отдельными вопросами, давать небольшие примеры и ревью, а не генерировать весь проект без запроса.
- Никакая из описанных реализаций не считается уже написанной; сначала изучить фактические файлы репозитория.
