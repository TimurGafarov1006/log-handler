# Log Analyzer

Учебный проект на Kotlin/JVM для анализа HTTP access logs и сравнения последовательной и параллельных реализаций. Цель — проверить корректность результатов и экспериментально исследовать влияние числа потоков, размера входа и других параметров на время работы.

## Текущее состояние

Реализованы модель `LogEntry`, парсер `LogParser`, чтение батчей `LogReader` и последовательный анализатор `SequentialAnalyzer`. Анализатор передаёт записи существующим `LogHandler`. `LogStatistics` накапливает и объединяет статистику, а `StatisticsHandler` подключает её к последовательному анализатору и `LogEngine`. `LogEngine` обрабатывает батчи в пуле с ограничением числа незавершённых задач; `Main.kt` содержит пример-заглушку.

## Чтение и последовательный анализ

Формат проверен по `access_large.log` (1 500 000 строк):

```text
2026-11-01 00:00:00 192.29.12.190 GET /api/orders 200 28
```

`LogParser.parse(line)` принимает семь полей, разделённых пробельными символами. Дата и время представлены как `LocalDateTime` без добавления часового пояса. Календарная дата проверяется строго; HTTP-статус должен быть в диапазоне 100–599, задержка — неотрицательным `Long` в миллисекундах. IP, метод и URL сохраняются как строки.

Некорректная строка, включая пустую, останавливает анализ: `LogReader` выбрасывает `IllegalArgumentException` с номером строки (от 1) и исходной причиной. Ошибки чтения и обработчиков передаются вызывающему коду. Уже обработанные батчи не откатываются.

```kotlin
LogReader.open(path, batchSize = 10_000).use { reader ->
    while (true) {
        val entries = reader.readBatch()
        if (entries.isEmpty()) break
        handler.handle(entries)
    }
}

SequentialAnalyzer(listOf(handler), batchSize = 10_000).analyze(path)
```

Здесь `path` — `java.nio.file.Path`, `handler` — реализация `LogHandler`. Размер батча должен быть положительным. Один reader открывается на весь анализ и закрывается при завершении или исключении. `readBatch()` возвращает отдельный список, последний батч может быть неполным; пустой список означает конец файла. Последовательный анализатор вызывает обработчики по порядку в вызывающем потоке, хранит один батч и не накапливает весь файл. Для независимого повторного анализа следует создавать новые обработчики со свежим состоянием.

Тесты проверяют парсер, границы батчей, ошибки, порядок записей и полный исходный файл. На полном файле результат сверяется с независимым построчным подсчётом числа записей, статусов, URL, IP, сумм и максимумов задержек, а также минутных окон и ошибок 5xx. Генератор дополнительных данных не добавлен: исходный файл уже есть, небольшие граничные наборы создаются тестами.

## Что должна делать программа

- Читать файл логов, не загружая его целиком в память.
- Подсчитывать общее число запросов и распределение HTTP-статусов, формировать топ URL и IP, вычислять среднее время ответа.
- Собирать статистику по минутным окнам: число запросов, ошибки 5xx, среднюю и максимальную задержку; определять пики нагрузки.
- Предоставлять последовательную и параллельную реализации с одинаковыми результатами на одном входе.
- Измерять полное время анализа и сохранять результаты экспериментов для построения таблиц и графиков.

## Общие договорённости

- До параллельной работы согласовать формат входа, политику ошибок, интерфейс анализатора и структуру результата.
- Последовательная и параллельная реализации должны давать одинаковую статистику; проверять это тестами на одном входе.
- Ограничивать очереди и число задач в работе, следить за использованием памяти, корректным завершением потоков и обработкой исключений.
- Не делать выводов о производительности без измерений. Для экспериментов фиксировать параметры запуска и характеристики окружения.
- Ускорение: `S = T_seq / T_parallel`; эффективность: `E = S / P`, где `P` — число рабочих потоков.
- Совместно подготовить итоговый отчёт (4–6 страниц), презентацию и защиту; распределение вклада и результаты каждого участника отразить в отчёте.

## Статистика запросов

`StatisticsHandler` реализует `LogHandler` и поддерживает конкурентные вызовы.
Для каждого независимого анализа создавайте новый обработчик. Пример последовательного анализа:

```kotlin
val handler = StatisticsHandler()
SequentialAnalyzer(listOf(handler), batchSize = 10_000).analyze(path)
val result = handler.snapshot()
println("Requests: ${result.requestCount}")
println("Average response time (ms): ${result.averageResponseTime}")
println(result.topUrls(10))
println(result.topIps(10))
println(result.peakMinutes(5))
```

Здесь `path` — `java.nio.file.Path`. Тот же обработчик подключается к параллельному движку:

```kotlin
val handler = StatisticsHandler()
LogEngine(listOf(handler), LogReader.open(path, 10_000)).process(path.toString())
val result = handler.snapshot()
```

`LogEngine` получает уже открытый reader; аргумент `process` сохранён для совместимости
и не выбирает входной файл. Движок сам закрывает reader и ожидает отправленные задачи.
Полный результат следует получать после завершения анализа. При ошибке ранее обработанные
батчи сохраняются; содержимое неуспешного батча не добавляется.

Снимок `StatisticsSnapshot` содержит количество запросов, распределение HTTP-статусов,
счётчики URL и IP, сумму, среднюю и максимальную задержку в миллисекундах, карту минутных окон.
Каждое окно содержит число запросов, число ответов 500–599, сумму, среднюю и максимальную задержку.
Окна определяются календарной минутой без часового пояса: `00:00:59` относится к `00:00`,
`00:01:00` — уже к `00:01`; разные даты не объединяются. В карту попадают только минуты с запросами.

`topUrls` и `topIps` сортируют по убыванию количества, при равенстве — по возрастанию строки
(лексикографически, в том числе для IP). `peakMinutes` сортирует по убыванию количества запросов,
при равенстве — от ранней минуты к поздней. По умолчанию возвращаются первые 10 элементов.
Лимит 0 возвращает пустой список, отрицательный лимит запрещён. Для пустого входа счётчики,
сумма, среднее и максимум равны нулю, карты и топы пусты.

`LogStatistics` — изменяемый накопитель для одного потока. `add(entry)` добавляет запись,
`merge(snapshot)` объединяет частичный результат. Средние вычисляются из суммы и количества,
а не усреднением средних батчей. Суммы задержек используют `BigInteger`, чтобы несколько
допустимых значений `Long` не вызывали переполнение; средние представлены как `Double`.
Полученные через `snapshot()` карты защищены от изменения и не связаны с дальнейшими обновлениями.

`StatisticsHandler` собирает локальную статистику батча без блокировки и объединяет её под общей
блокировкой; получение снимка использует ту же блокировку. Порядок завершения батчей не влияет
на итоговые счётчики, топы и пики. Обработчик хранит агрегаты, а не все записи; объём памяти
растёт с числом уникальных URL, IP и минут. Объединение и копирование снимка выполняются
последовательно; ускорение этой реализации без измерений не гарантируется.

Тесты проверяют известные значения статистики, объединение разных разбиений, равенство топов
при перестановке записей, границы минут и дат, пустой вход, переполнение суммы `Long`,
независимость снимков и конкурентные вызовы. Интеграционный тест сверяет статистику на всех
1 500 000 строках с независимым построчным подсчётом и сравнивает оба движка.

Для полного интеграционного теста Gradle задаёт тестовой JVM лимит heap 2 ГБ: одновременно
сравниваются карты эталонного подсчёта и анализаторов с большим числом уникальных IP.
