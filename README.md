# LogHandler — анализатор серверных журналов

Учебный проект по параллельному программированию на Kotlin/JVM. Программа читает журнал HTTP-запросов и вычисляет сводную статистику. Две реализации решают одну задачу: последовательная обрабатывает данные в вызывающем потоке, а параллельная распределяет обработку пакетов между потоками и объединяет частичные результаты.

## Задача и данные

На вход подаётся текстовый файл: одна строка соответствует одному запросу. Поля разделены пробелами:

```text
2026-11-01 00:00:00 192.168.1.10 GET /api/users 200 45
```

Поля: дата и время (`yyyy-MM-dd HH:mm:ss`), IP-адрес, HTTP-метод, URL, код ответа и время ответа в миллисекундах. Код ответа должен быть в диапазоне 100–599, время — неотрицательным целым числом. При ошибке формата программа останавливается и сообщает номер строки.

На выходе программа показывает количество запросов, распределение HTTP-статусов, среднее и максимальное время ответа, наиболее частые URL и IP-адреса. Для минут с наибольшим числом запросов выводятся количество запросов, число ответов 5xx, среднее и максимальное время ответа. Полный результат можно сохранить в JSON. При одинаковой частоте URL и IP сортируются по значению, а пиковые минуты — по времени.

В репозитории есть пример входных данных `access_large.log`: 1 500 000 строк, около 84 МиБ. Можно использовать и собственный файл того же формата.

## Требования и запуск

- JDK 25; проект использует Gradle Wrapper и Kotlin/JVM.
- При первом запуске Gradle необходим доступ к сети для загрузки дистрибутива и зависимостей.
- Для полного набора тестов и анализа большого примера настройками проекта предусмотрено до 2 ГиБ кучи JVM.

Из корня проекта:

```bash
./gradlew test
./gradlew installDist
./build/install/LogHandler/bin/LogHandler access_large.log --mode sequential
./build/install/LogHandler/bin/LogHandler access_large.log --mode parallel --batch-size 10000 --top 10 --output report.json
```

В Windows используйте `gradlew.bat`, а после сборки — `build\install\LogHandler\bin\LogHandler.bat`. Справка по аргументам: `./build/install/LogHandler/bin/LogHandler --help`.

| Параметр | Назначение | По умолчанию |
| --- | --- | --- |
| `--mode sequential\|parallel` | Последовательная или параллельная обработка | `sequential` |
| `--batch-size N` | Число строк в пакете, целое число больше нуля | `10000` |
| `--top N` | Размер списков популярных URL, IP и пиковых минут; `0` скрывает списки в консоли | `10` |
| `--output FILE` | Сохранить полный отчёт в JSON | Не сохранять |
| `--help` | Показать справку | — |

Путь к файлу с пробелами нужно заключить в кавычки. JSON содержит все счётчики по URL, IP и минутам; параметр `--top` ограничивает только отдельные списки лидеров. Существующая папка для файла JSON должна быть создана заранее. Исходный журнал нельзя указать в качестве файла отчёта.

## Алгоритм и параллелизм

Записи можно разбить на независимые пакеты: для каждого достаточно посчитать локальные счётчики, суммы и максимумы, а затем объединить их. Благодаря этому обработка разных пакетов может выполняться одновременно, сохраняя тот же итог, что и последовательный проход.

1. `LogReader` последовательно читает файл, разбирает строки и формирует пакет объектов `LogEntry`.
2. В последовательном режиме `SequentialAnalyzer` сразу передаёт пакет обработчику статистики в том же потоке.
3. В параллельном режиме `LogEngine` передаёт пакеты пулу потоков. Число потоков определяется через `Runtime.getRuntime().availableProcessors()`.
4. `StatisticsHandler` собирает отдельную статистику пакета. Затем он объединяет её с общей статистикой внутри блока `synchronized`; общие данные не изменяются одновременно несколькими потоками.
5. После чтения последней строки программа ожидает завершения задач, закрывает файл и пул, формирует снимок статистики и выводит отчёт.

Число незавершённых задач ограничено числом рабочих потоков: когда предел достигнут, чтение ожидает завершения ранее отправленного пакета. Это ограничивает объём данных в очереди. При этом память для итоговых счётчиков зависит от числа различных IP, URL и минут. Ошибки разбора и обработки не считаются успешным результатом.

Чтение и разбор строк остаются последовательными. Возможные ограничения ускорения — скорость чтения файла, последовательный разбор, стоимость передачи задач, слияние статистики под блокировкой, сборка мусора и объём памяти. Эффект зависит от размера файла, размера пакета, числа доступных процессоров и характеристик машины.

## Проверка корректности

Тесты проверяют разбор строк, обработку ошибок, накопление и объединение статистики, работу CLI и равенство результатов последовательного и параллельного режимов. Интеграционный тест сравнивает статистику на полном `access_large.log`, в том числе счётчики, времена и минутные окна. Команда запуска всех тестов — `./gradlew test`.

## Исследование производительности

CLI выводит `Analysis time (ms)` — время от начала анализа до получения итогового снимка, включая чтение, разбор и обработку файла. Вывод в консоль и запись JSON в это измерение не входят. Один запуск сам по себе не является надёжным бенчмарком: результаты зависят от прогрева JVM, кеша файловой системы и нагрузки на машину.

Для исследования нужно использовать одинаковые входные данные для обоих режимов и сначала проверить совпадение статистики. Затем выполнить несколько повторов, записать условия эксперимента и представить медианы в таблицах и графиках. Варьируемые параметры:

- размер входа, например 100 000, 500 000 и 1 500 000 строк;
- число доступных процессоров для параллельного режима, например 1, 2, 4 и 8;
- размер пакета, например 1 000, 10 000 и 100 000 строк.

Отдельного аргумента числа потоков в CLI нет. На JVM с поддержкой `-XX:ActiveProcessorCount` его можно задать для запуска приложения, например:

```bash
JAVA_TOOL_OPTIONS=-XX:ActiveProcessorCount=4 ./build/install/LogHandler/bin/LogHandler access_large.log --mode parallel --batch-size 10000
```

Для каждого размера входа и числа потоков `P` ускорение обычно рассчитывают как `S = T_seq / T_par`, а эффективность как `E = S / P`, где времена измерены в одинаковых условиях. В тексте задания формула ускорения записана в обратном порядке (`T_par / T_seq`); при подготовке отчёта обозначения и принятую формулу следует согласовать с преподавателем.

По измерениям нужно обсудить, когда параллельная обработка окупает накладные расходы, как размер входа влияет на эффективность, при каком числе потоков дальнейшее ускорение уменьшается и какие ограничения становятся определяющими. Готовые результаты измерений, таблицы и графики в текущем репозитории отсутствуют; автоматического запуска серии экспериментов здесь нет.

## Структура проекта

```text
src/main/kotlin/     модели, чтение и разбор, анализаторы, статистика и CLI
src/test/kotlin/     модульные и интеграционные тесты
access_large.log     пример входного журнала
build.gradle         зависимости, настройки JVM и тестов
gradlew              Gradle Wrapper
```

По условиям задания для сдачи также нужны `Makefile`, отчёт на 4–6 страниц и презентация для защиты продолжительностью 10–15 минут. Этих материалов в текущем репозитории пока нет.
