# Log Analyzer

Учебный проект на Kotlin/JVM для анализа HTTP access logs и сравнения последовательной и параллельных реализаций. Цель — проверить корректность результатов и экспериментально исследовать влияние числа потоков, размера входа и других параметров на время работы.

## Текущее состояние

Реализованы модель `LogEntry`, парсер `LogParser`, чтение батчей `LogReader` и последовательный анализатор `SequentialAnalyzer`. Анализатор передаёт записи существующим `LogHandler`; накопление статистики реализуется в обработчиках участником 3. `LogEngine` остаётся заготовкой параллельной версии, `Main.kt` содержит пример-заглушку.

## Чтение и последовательный анализ

Формат проверен по `access_large.log` (1 500 000 строк):

```text
2026-11-01 00:00:00 192.29.12.190 GET /api/orders 200 28
```

`LogParser.parse(line)` принимает семь полей, разделённых пробельными символами. Дата и время представлены как `LocalDateTime` без добавления часового пояса. Календарная дата проверяется строго; HTTP-статус должен быть в диапазоне 100–599, задержка — неотрицательным `Long` в миллисекундах. IP, метод и URL сохраняются как строки.

Некорректная строка, включая пустую, останавливает анализ: `LogReader` выбрасывает `IllegalArgumentException` с номером строки (от 1) и исходной причиной. Ошибки чтения и обработчиков передаются вызывающему коду. Уже обработанные батчи не откатываются.

```kotlin
LogReader.open(path, batchSize = 10_000).use { reader ->
    while (true) {
        val entries = reader.readBatch()
        if (entries.isEmpty()) break
        handler.handle(entries)
    }
}

SequentialAnalyzer(listOf(handler), batchSize = 10_000).analyze(path)
```

Здесь `path` — `java.nio.file.Path`, `handler` — реализация `LogHandler`. Размер батча должен быть положительным. Один reader открывается на весь анализ и закрывается при завершении или исключении. `readBatch()` возвращает отдельный список, последний батч может быть неполным; пустой список означает конец файла. Последовательный анализатор вызывает обработчики по порядку в вызывающем потоке, хранит один батч и не накапливает весь файл. Для независимого повторного анализа следует создавать новые обработчики со свежим состоянием.

Тесты проверяют парсер, границы батчей, ошибки, порядок записей и полный исходный файл. На полном файле результат сверяется с независимым построчным подсчётом числа записей, статусов, URL, IP, сумм и максимумов задержек, а также минутных окон и ошибок 5xx. Генератор дополнительных данных не добавлен: исходный файл уже есть, небольшие граничные наборы создаются тестами.

## Что должна делать программа

- Читать файл логов, не загружая его целиком в память.
- Подсчитывать общее число запросов и распределение HTTP-статусов, формировать топ URL и IP, вычислять среднее время ответа.
- Собирать статистику по минутным окнам: число запросов, ошибки 5xx, среднюю и максимальную задержку; определять пики нагрузки.
- Предоставлять последовательную и параллельную реализации с одинаковыми результатами на одном входе.
- Измерять полное время анализа и сохранять результаты экспериментов для построения таблиц и графиков.

## Распределение работы

Роли можно закрепить за именами участников. Объём задач ориентировочный: детали интерфейсов стоит согласовать вместе до начала работы.

### Участник 1 — автор каркаса: интеграция и запуск

Небольшая часть работы с учётом уже написанного каркаса:

- Заменить заглушку в `Main.kt` запуском готовых компонентов: путь к файлу, выбор реализации и основные параметры.
- Собрать результаты работы участников в одну запускаемую программу, помочь согласовать интерфейсы и проверить совместный запуск.
- Обновить инструкции запуска в README и подготовить `Makefile` для основных команд проекта.

### Участник 2 — чтение, парсинг и последовательный анализ

- Сверить формат входа с реальными данными, согласовать представление времени и обработку некорректных строк.
- Доработать модель и парсер; добавить тесты для корректных и некорректных строк.
- Исправить чтение батчей: открывать и закрывать файл на протяжении всего анализа, корректно обрабатывать конец файла и последний неполный батч.
- Реализовать последовательный анализатор как эталон для проверки параллельной версии.
- При необходимости подготовить генератор входных данных разных размеров.

### Участник 3 — статистика и корректность

- Спроектировать структуру статистики: счётчики, распределения, суммы и количества для средних, минутные окна.
- Реализовать накопление и объединение частичных результатов; согласовать её использование с участниками 2 и 4.
- Определить правила сортировки при равных значениях в топах и представление пустого результата.
- Написать тесты агрегации и объединения, а также сравнения полных результатов последовательного и параллельного анализаторов на одинаковых данных.
- Проверить пустой файл, неполный батч, ошибки входа и другие граничные случаи.

### Участник 4 — параллельный анализ и эксперименты

- Доработать `LogEngine` или реализовать параллельный анализатор: один поток читает батчи, фиксированный пул обрабатывает их, частичные результаты объединяются.
- Ограничить число незавершённых задач, чтобы очередь не росла бесконтрольно; обеспечить завершение на конце файла, ожидание задач, закрытие ресурсов и распространение ошибок.
- Совместно с участником 3 проверить равенство результатов последовательной и параллельной версий.
- Подготовить запуск экспериментов: прогрев JVM, несколько повторов, медиана, экспорт результатов в CSV и графики.
- Исследовать влияние размера входа, числа потоков и размера батча; рассчитать ускорение и эффективность, описать узкие места и насыщение по фактическим измерениям.
- При наличии времени рассмотреть альтернативный конвейер или общую конкурентную агрегацию как отдельный вариант для сравнения.

## Общие договорённости

- До параллельной работы согласовать формат входа, политику ошибок, интерфейс анализатора и структуру результата.
- Последовательная и параллельная реализации должны давать одинаковую статистику; проверять это тестами на одном входе.
- Ограничивать очереди и число задач в работе, следить за использованием памяти, корректным завершением потоков и обработкой исключений.
- Не делать выводов о производительности без измерений. Для экспериментов фиксировать параметры запуска и характеристики окружения.
- Ускорение: `S = T_seq / T_parallel`; эффективность: `E = S / P`, где `P` — число рабочих потоков.
- Совместно подготовить итоговый отчёт (4–6 страниц), презентацию и защиту; распределение вклада и результаты каждого участника отразить в отчёте.
